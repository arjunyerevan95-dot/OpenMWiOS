## Objective

Deliver an implementation-ready, source-verified and executable-tested design for repeatable exterior-renderer capture. It must distinguish missing coverage, depth rejection, incorrect fog inputs/calculation, faulty sky render-to-texture output, and incorrect final composition without relying on an exact startup frame or unexplained center-pixel color changes.

This is the pre-build engineering gate, not another speculative renderer correction. Produce useful executable validation and a concrete integration plan, then stop for orchestrator review. No new IPA or production-source modification is authorized by this order. A later canonical amendment/order and explicit directive are required for integration and CI; passing local tests does not release that gate automatically.

## Phase 1 — one end-to-end rendering model

Trace and document the actual paths for opaque objects/rocks, alpha-tested foliage, terrain, sky RTT, and final presentation. For each relevant seam record commit, file/symbol, producer, consumer, state inheritance/override, framebuffer/viewport identity, and shader variant. Cover:

1. camera/projection and geometry coverage;
2. depth test/write and drawable/material identity;
3. effective fog inputs, fog factor, and shader/program consumption;
4. sky RTT attachment creation, render output, texture binding and sampling coordinates; and
5. final composition and presentation.

Do not assume all passes share uniforms, distance conventions, viewport coordinates or state ownership. Distinguish OSG intent, GL4ES tracked state and native GLES state. Correct upstream fog receipt does not prove correct final pixels.

Produce a discrimination matrix: each suspected failure class, the observation that would support it, the observation that would rule it out, and what remains ambiguous. Center RGBA equality and projected bounds alone must never imply missing coverage. A color-changing draw alone must not imply it owns the final displayed pixel across multiple render targets.

## Phase 2 — implement and test the capture-state contract locally

Implement a small reusable controller prototype with deterministic executable tests, not only source-string assertions. Demonstrate:

- no startup/first-exterior auto-consumption; the user can reach the desired scene before requesting capture;
- explicit arm -> capture -> complete/error behavior with a unique request/session/frame identity;
- at least two independent captures in the same process after completion, plus a clean fresh-process state;
- requests at loading/interior/invalid times remain pending or fail explicitly, never silently capture the wrong scene;
- duplicate/in-progress requests, cancellation, timeout, budget exhaustion and failed output writes have deterministic terminal results without leaking an armed state;
- resource limits apply per capture with a separate bounded session limit; startup or unrelated frames cannot consume the target budget;
- disabled mode does no capture work; completion/failure returns to normal mode; and
- framebuffer/viewport mismatch, unavailable depth/sky channels, same-color writes and incomplete evidence are represented as insufficient, not successful attribution.

Specify one low-friction device trigger using existing accessible facilities and a visible/verifiable acknowledgement. Verify its source integration seam and threading/lifetime model. It must not require a new touch gesture, a restart at an exact view, blind timing, or per-capture rebuilds. Do not implement the production trigger in this phase.

## Phase 3 — concrete observation and reference plan

Specify the smallest feasible debug-output set for the existing iOS/GLES backend:

- normal reference image;
- geometry coverage and rendered depth visualization;
- effective fog factor/color;
- sky texture before final composition; and
- final composition, all associated with actual pass/frame identities.

Do not propose unsupported raw GLES depth readback as if it already works. For each channel, prove the API/source seam and explain limitations. Shader-encoded depth/coverage and deliberately altered debug views are permissible DESIGN candidates. Such views must be labeled diagnostic, isolated from ordinary output, and must not be presented as renderer corrections or assumed presentation-neutral. Address transparency/discard, depth semantics, resource lifetime, readback alignment, coordinate transforms and restoration of graphics state. If multi-view capture spans frames, specify how camera/time/weather are held or mismatches detected.

Define two reproducible real-game targets (silhouette and horizon) with save/config/content identities and camera/weather/time metadata, reusing existing evidence where available. Specify a same-revision desktop comparison if an existing build is available. If not, record the prerequisite and use synthetic expected outputs for the local contract; do not claim those qualify the real engine or block indefinitely trying to build desktop OpenMW.

Include a compact recommendation on the first coherent correction boundary. Explicit fog uniforms and the shared native-GLES3 fork are candidates to assess, not preselected fixes. Identify adoption dependencies and what evidence would choose a boundary repair versus a broader renderer migration. No full rewrite, external-fork merge, or speculative fix is authorized.

## Acceptance and review gate

Successful completion requires:

1. a source-backed rendering/state model for the two target families;
2. runnable fixture code, commands and results proving the capture-state contract, including repeatability and failure handling;
3. every proposed observation mapped to a feasible source/API path, with unsupported assumptions called out;
4. a discrimination matrix that can produce either a supported classification or an honest insufficient result;
5. a practical device/reference protocol without first-frame timing or obligatory new UI work;
6. a minimal file/symbol-level integration plan, expected test coverage, explicit limitations and proposed bounded build budget; and
7. no product-source, CI/configuration, canonical-file or device-setting change.

Host fixture success proves only the tested logic. It does not establish iOS GPU behavior, a renderer cause, or a corrected runtime milestone. The orchestrator must review the proposed observability against the desired conclusions before issuing any implementation/build authority. This is an orchestrator review, not a requirement for the user to draft or approve technical specifications.
