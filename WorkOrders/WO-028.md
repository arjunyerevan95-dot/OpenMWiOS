## Objective

Faithfully adapt the recent Android OpenMW touch-control interface and its semantic action-dispatch behavior to iOS. WO26 already established touch movement, look, traversal, fullscreen rendering, UI, audio, and scene transitions. WO28 must replace the sparse keyboard/mouse approximation with the Android-derived functional control set while preserving the qualified renderer and WO27 runtime data-path correction.

Primary milestone:

> The early Morrowind sequence is controllable through a touch interface that functionally matches recent OpenMW Android rather than merely approximating keyboard/mouse inputs.

## Established baseline

- WO27 runtime-resolves the current Documents directory and requires no persisted sandbox UUID for the default game-data path.
- WO26 touch movement/look permit ship traversal and Seyda Neen exterior access.
- Fullscreen rendering, UI, audio, and scene transitions are qualified.
- Inventory is currently broken: the iOS overlay injects keyboard `B`, while the corresponding active OpenMW behavior is consumed through another semantic input path observed as right mouse/controller `B` behavior.
- Exterior foliage alpha, distance/horizon rendering, water classification, reduced render scale 0.58, and cache reliability are separate boundaries.

## Scope

1. Identify the exact recent Android reference repository, tag, commit, overlay/layout source, assets, native bridge, OpenMW input patches, action definitions, and GUI/gameplay visibility behavior.
2. Inventory every Android on-screen control and its full press/release/hold/repeat dispatch chain.
3. Inventory the current iOS controls and classify each Android control as `MATCHES`, `MISSING`, `WRONG ACTION`, `WRONG EVENT TYPE`, `WRONG VISIBILITY`, `WRONG LAYOUT`, `PARTIAL`, or `NOT APPLICABLE`.
4. Correct action dispatch first, beginning with Inventory. Prefer Android-equivalent semantic/virtual input events feeding OpenMW's existing input manager; do not guess keyboard letters.
5. Port the Android-equivalent early-game control set: movement, look, activate/use, attack, jump, ready weapon, ready magic, inventory, journal/menu, sneak where applicable, and other standard Android actions proven by source.
6. Match Android gameplay/GUI visibility and dispatch behavior across dialogue, inventory, journal, character creation, text entry, and pause/menu states.
7. Preserve independent touch ownership for simultaneous movement + look + action.
8. Preserve a runtime-derived, safe-area-aware layout across wide/smaller iPhones, landscape iPad, and arbitrary supported landscape dimensions.
9. Reproduce Android functional grouping and approximate placement without blocking on final artwork.

## Action-dispatch contract

Preferred architecture:

`touch control → Android-equivalent semantic/virtual input action → existing OpenMW input manager → configured OpenMW action`

Hardcoded keyboard events are permitted only where the Android source intentionally uses that exact keyboard event. Inventory acceptance is explicit:

- Before: touch Inventory → keyboard `B` → inventory does not open.
- After: touch Inventory → correct OpenMW action → inventory opens and can be closed through touch.

## Layout and movement requirements

- No device model or current-device resolution may be hardcoded.
- Layout must derive from logical runtime geometry and safe-area information.
- The Android fixed joystick is the baseline fidelity target.
- A floating/dynamic left joystick is the preferred later iOS refinement. It may be implemented only as a separate reviewable change if trivial and non-blocking; otherwise it must remain the first recommended UX refinement.

## Required regression coverage

- Android-to-iOS action mapping.
- Inventory, attack, activate, jump, weapon, magic, journal/menu actions.
- Press/release, hold, and applicable repeat behavior.
- Touch-ID ownership and movement + look + action.
- Gameplay/GUI mode transitions and native text entry preservation.
- Safe-area layout for wide and smaller iPhones, landscape iPad, and arbitrary landscape dimensions.
- No current-device dimensions.
- Existing touch tests, renderer baseline, native scale 1.00, and WO27 data-path behavior.

## Build and validation policy

- One Fast Development production build after local qualification.
- Full Qualification must not run.
- Cache architecture must not change; a miss is recorded, not repaired here.
- The worker does not launch OpenMW. The user performs one controlled device run after data-path, scale, logging, and artifact preflight.
- usbmux is useful but not a qualification gate when unavailable.

Controlled device sequence:

1. Launch and navigate the main menu through touch.
2. Start or continue the game.
3. Validate movement, look, and simultaneous movement + look.
4. Validate Activate, Attack, Jump, Inventory open/use/close, Journal/menu, and weapon/magic actions.
5. Validate dialogue, a scene transition, and movement + look + action with independent touch ownership.

## Prohibited changes

- Renderer, native scale, fullscreen path, OSG, GL4ES, shader compatibility, FBO mapping, fragment linkage, VFS/MWUI, or scene-rendering changes.
- WO27 runtime data-path architecture or return of UUID/manual-config workarounds.
- Exterior foliage, distance/horizon, water, ColorMaski, reduced-scale, or performance tuning.
- Cache redesign, Full Qualification, Nexus artwork integration, or unrelated cleanup.
